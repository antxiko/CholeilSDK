; Uncompressed graphics blocks stored as SPRITE MOSAICS rather than a flat
; row-major tile raster -- tiles within each sprite are in Mega Drive
; COLUMN-MAJOR order (tile0=col0/row0, tile1=col0/row1, ...), and sprites are
; placed left-to-right/top-to-bottom in a macro grid. Naive row-major
; rendering (raw_graphics.txt/RawGraphicsExtractor) produces a scrambled mess
; for these -- use SpriteGraphicsExtractor/Inserter instead.
; Format: 0xADDRESS,lengthBytes,spritesPerRow,spriteTilesWide,spriteTilesTall[,tileOrder]
; tileOrder is "colmajor" (default, the Mega Drive sprite convention) or
; "rowmajor" for blocks that are DMAd into VRAM as a plain tile run, whose
; tiles read TL, TR, BL, BR. Get it wrong and the quadrants come out swapped
; -- the round trip still reinserts byte-exact, but the PNG is unusable.
;
; 0x00a8d36: the "Soleil" title logo. Found by watching the emulator: a VRAM
; write breakpoint at 0x80C0 (sprite tile index 0x406, the first tile of the
; on-screen logo sprite at tile 0x412) showed the source read at ROM 0xa8d56
; -- but that tile turned out to be the SECOND real tile, not the first: there's
; one more (near-blank) tile immediately before it. True start is 0xa8d36.
; 14 sprites of 4x4 tiles (16 tiles/sprite), 7 sprites per row x 2 rows = 224
; tiles = 7168 bytes, ending exactly at 0xaa956 -- right before "PULSA START"'s
; real data at 0xaa9b2 (no overlap; going one sprite further pulls in PULSA
; START's pixels as garbage, confirming this end boundary).
;
; Palette not confirmed yet -- currently rendered/decoded with a palette
; reverse-derived from a player-supplied reference screenshot (dominant
; quantized colors sorted by luminance), which visually matches well but is
; NOT a traced, ground-truth CRAM palette. Replace with a real one (e.g. via
; a CRAM write breakpoint in the emulator) when available.
0xa8d36,7168,7,4,4
; The ground-money coin ("Malin") pickup: 8 tiles per copy = two 16x16 sprite
; poses (face with diagonal shine / thin edge, alternated to spin). The zone
; sprite strip re-uploads the current pose via DMA to VRAM tiles 760-767;
; the two blocks below are the two spin poses -- edit BOTH consistently.
; Found via VRAM diff of an in-game savestate (only animated tiles change)
; + literal byte search in ROM (blocks are uncompressed).
; The coin animation actually cycles through EIGHT consecutive 256-byte blocks
; at 0xd0f60 + n*0x400 (found by dumping VRAM tiles 760-767 every frame and
; matching against ROM with ALL occurrences, not just the first). In the
; original ROM they held only two designs: edge-on (d0f60, d1360, d1f60,
; d2360) and face (d1760, d1b60, d2760, d2b60 -- four identical copies).
; The per-frame cycle: edge x8, face(d2760/d2b60) x8, edge x8, face(d1760) x4,
; face(d1b60) x4. Edit copies of the same pose consistently.

; MORE COPIES OF THE SAME COIN, found after the first pass shipped and the
; coin looked right in one zone and wrong in others. The eight blocks above
; are not the only place this art lives; searching the ROM for the two poses
; -- exact, and then allowing variant pixels -- turns up these, and the face
; pose (the distinctive one) exists in exactly nine places in total: the four
; above, 0xf4680, the two shadowed copies below, and the two map-plane copies
; at 0xe45e0/0xe46e0.
;
; 0xf4600: one 512-byte pickup strip loaded by Choleil's graphics family to
; VRAM tiles 0x7F0-0x7FF. It contains four 16x16 sprites in COLUMN-MAJOR order:
; coin edge at 0xf4600, a coin-like face at 0xf4680, then two exact red-apple
; copies at 0xf4700 and 0xf4780. The final two used to fall outside this
; registry entry, leaving enemy-dropped apples uneditable. Snapshot 5 proved
; that the visible golden apple does NOT use 0xf4680; its real two-frame art is
; in compressed block 0xa5644 and has a separate editor (see MANZANAS.md).
; 0xd6d20 + n*0x200: a second animation family, edge/face/edge/face, whose art
; is the same drawing plus a drop shadow -- 16 nibbles that are transparent
; (index 0) above are index 11 here. Row-major, 128 bytes = one pose each.
; 0xe45e0, 0xe46e0: two face-pose copies used as 16x16 tiles on a map plane,
; not as hardware sprites. Identified in Playa Anemona from savestate VRAM:
; tiles 688-691, referenced by the plane map at VRAM 0xc310. Each is followed
; by an edge-pose copy at 0xe4660/0xe4760. The edge has a small shading
; difference (6 nibbles) and was not redrawn.
